# Loop Engineering 段階導入計画

Addy Osmani の [Loop Engineering](https://addyo.substack.com/p/loop-engineering) をもとに、このリポジトリへ「エージェントを自分でプロンプトする」から「エージェントをプロンプトする仕組みを設計する」への移行を段階的に導入する計画。

## 設計理論の要点

ループに必要なのは5つの部品と1つのメモリ。

| # | 部品 | 役割 | Claude Code での実現 |
|---|------|------|---------------------|
| 1 | Automations | 定期起動でタスク発見・トリアージ(ハートビート) | スケジュールタスク / hooks / GitHub Actions |
| 2 | Worktrees | 並列エージェントのファイル衝突防止 | `git worktree` / サブエージェントの worktree 分離 |
| 3 | Skills | プロジェクト知識の外部化(毎回説明しない) | `SKILL.md` |
| 4 | Plugins / Connectors | 実ツール(Issue/CI/Slack等)への接続 | MCP / プラグイン |
| 5 | Sub-agents | 作る者と検証する者の分離(maker/checker) | `.claude/agents/` |
| +1 | **メモリ** | セッションを跨いで「何が済んで次は何か」を保持 | リポジトリ内の markdown |

原則:

- **停止条件は機械検証可能に**する(「テストとlintが通る」など)。書いた本人に採点させない。
- **メモリはディスクに**置く。モデルは忘れるがリポジトリは忘れない。
- **検証責任は人間に残る**。ループが速いほど comprehension debt も速く積もる。コードは読む。
- **トークンコストに注意**。サブエージェントや定期実行は消費が跳ねる。価値のある所にだけ使う。

## 現状マッピング(2026-07-02)

- 検証手段: `npm run lint`(ESLint)、`tsc -b`(型)。**テストなし** → フェーズ0で解消
- CI: SonarCloud / summary のみ
- メモリ: なし → フェーズ1で導入
- スキル / サブエージェント / 自動化: なし

## フェーズ計画

### フェーズ0: 検証基盤(green の定義)— ✅ 今回実装

ループの前提。機械検証可能な「完了」がなければループは自己採点できない。

- Vitest 導入、`src/utils/` のユニットテスト作成(random / constants)
- `npm run check` = 型チェック + lint + テスト を1コマンド化。以後これがループの停止条件
- **完了条件**: `npm run check` が green

### フェーズ1: 最小ループ(スキル + メモリ)— ✅ 今回実装

まだ「手動で起動する1本のループ」。ただし知識と状態は外部化する。

- スキル `loop/skills/loop-runner/`(実体はリポジトリで管理し、`$CLAUDE_CONFIG_DIR/skills/` へ symlink で登録): バックログから1件取り、実装し、`npm run check` が green になるまで反復する手順を記述
- メモリ `loop/BACKLOG.md`(やることリスト)+ `loop/STATE.md`(実行ログ: 試したこと・結果・次)
- 使い方: セッションで「loop-runner スキルに従ってバックログを1件進めて」と言うだけ。細かい指示は不要になる
- **完了条件**: 新しいセッションが BACKLOG だけを頼りにタスクを1件完了し、STATE に記録を残せる

### フェーズ2: Maker / Checker 分離(サブエージェント)

書いた本人は自分の宿題に甘い。検証者を分ける。

- `loop/agents/implementer.md`(→ `.claude/agents/` に配置): 実装担当。BACKLOG の1件を実装
- `loop/agents/verifier.md`(→ 同上): 検証担当。差分を仕様(CLAUDE.md・スキル)と突き合わせ、`npm run check` を実行し、指摘を返す。**実装はしない**
- loop-runner スキルを「implementer → verifier → 指摘があれば差し戻し(最大2往復)」の流れに更新
- **完了条件**: verifier が implementer の不備を1件以上実際に検出して差し戻せること(意図的にバグを混ぜて演習する)
- 注意: トークン消費は約2倍。検証の価値がある変更にだけ使う

### フェーズ3: 並列化(Worktrees)

- `git worktree` で独立チェックアウトを作り、複数バックログ項目を並列に処理(サブエージェントの `isolation: worktree` 利用)
- ブランチ運用: `loop/<タスク名>` ブランチ → 人間レビュー → merge
- **完了条件**: 2件のタスクが衝突なく並列完了し、両方 green でマージできる
- 注意: 上限はツールではなく**自分のレビュー帯域**(orchestration tax)。並列数は2から

### フェーズ4: 自動化(ハートビート)

ここで初めて「ループ」が自走する。

- トリアージスキル `loop-triage` : lint 警告・TODO コメント・依存の古さ・CLAUDE.md と実装の乖離(例: localStorage キーの記述ずれ)を走査し、発見を BACKLOG に追記。**発見ゼロなら何も書かない**
- 起動方法(段階的に): ① 手動で週1回 → ② Claude のスケジュールタスクで毎朝実行 → ③ hooks(セッション終了時に STATE 更新を強制)
- 人間の役割: 朝 BACKLOG を見て、やる/やらないを判断するだけ(トリアージ受信箱)
- **完了条件**: 1週間、自分でタスクを「探す」作業をしていないこと

### フェーズ5: 接続と共有(Plugins / Connectors)

- MCP コネクタで GitHub Issues をメモリの外部版に昇格(BACKLOG.md → Issues 同期、PR 自動作成)
- 必要なら GitHub Actions 上で夜間ループ(ローカルを閉じても動く)
- スキル+エージェント+コネクタ一式をプラグイン化してチームに配布
- **完了条件**: 「Issue 起票 → ループが PR 作成 → CI green → 人間レビュー」が一連で流れる

## 運用ルール(全フェーズ共通)

1. **設定ファイルの配置**: スキル等の実体はリポジトリ(`loop/skills/` など)で管理し、`$CLAUDE_CONFIG_DIR`(`~/.claude-config/lucky-slot-roulette-for-ps/`)へ symlink で登録する。`~/.claude/` は触らない(CLAUDE.md 参照)
2. **停止条件**: ループの「完了」は常に `npm run check` green + 差分レビュー。3回連続で green にできなければ人間にエスカレーション
3. **メモリ更新**: ループの各実行は必ず `loop/STATE.md` に1行以上残す(日付 / 対象 / 結果 / 次)
4. **人間の責務**: マージ判断・BACKLOG の優先順位・ループが作ったコードを読むこと。ループに任せるのは作業であって判断ではない

## 進め方の目安

各フェーズは前のフェーズの完了条件を満たしてから。1フェーズ = 1〜2週間の運用で慣らし、うまく回らない部品(スキルの記述不足など)を直してから次へ進むこと。
