Addy Osmani の記事 [Loop Engineering](https://addyo.substack.com/p/loop-engineering) の設計理論を、StandUp ファシリテーター抽選ツールに段階導入した記録です。1週間で「エージェントに毎回指示を書く」状態から「バックログを置けばエージェントのペアが実装・検証して記録を残す」状態まで到達しました。実装より運用の学びが多かったので、同じことを試したいチーム向けにまとめます。

## ループエンジニアリングとは

「エージェントをプロンプトする人」を自分からシステムに置き換える考え方です。ループは5つの部品(Automations / Worktrees / Skills / Plugins・Connectors / Sub-agents)と1つのメモリ(セッションを跨いで状態を保持するファイル)で構成されます。重要な原則は3つ: 停止条件は機械検証可能にする(自己申告の「できました」を信用しない)、メモリはディスクに置く(モデルは忘れるがリポジトリは忘れない)、そして検証責任は人間に残る(ループが速いほどコードを読まないと理解が腐る)。

全体計画は [loop-engineering-plan.md](./loop-engineering-plan.md) を参照。フェーズ0〜5のうち、現時点でフェーズ2まで実装・運用済みです。

## 作ったもの

| 構成要素 | 場所 | 役割 |
|----------|------|------|
| 検証コマンド | `npm run check`(tsc + ESLint + Vitest) | ループの唯一の停止条件。「green」の定義 |
| バックログ | `loop/BACKLOG.md` | やることリスト。ループの入力(未来) |
| 実行ログ | `loop/STATE.md` | 各サイクルの結果と「次」(過去) |
| ルール集 | `loop/LEARNINGS.md` | 失敗から抽出した行動ルール(蒸留された知識) |
| スキル | `loop/skills/loop-runner/` | ループ1サイクルの手順書。セッションに「バックログを進めて」と言うだけで回る |
| エージェント | `loop/agents/implementer.md`・`verifier.md` | maker と checker。書く者と検証する者を分離 |

1サイクルの流れ: STATE と LEARNINGS を読む → BACKLOG から1件取る → implementer が実装 → verifier が差分を独立検証(APPROVE / REJECT、差し戻し最大2往復)→ check green → 記録 → 失敗があれば LEARNINGS にルール化。マージ判断は常に人間です。

## 導入の歩み

**7/2 フェーズ0+1(基盤)**: テストが1本もない状態からスタート。Vitest と `npm run check` を導入し、スキルとメモリファイルを作成。初期バックログ3件を投入。

**7/2〜7/7 最小ループの運用**: ドキュメント同期、抽選の重み付けロジックのテスト、useLocalStorage のテストと、1日1サイクルのペースで消化。この間に「フックはテストできる形にロジックを純粋関数抽出してから」等のパターンが LEARNINGS に蓄積され始めました。

**7/7 フェーズ2(maker/checker 分離)**: implementer と verifier を分離。完了条件は「verifier が実装の不備を実際に検出できること」としたため、意図的にバグを仕込む演習を実施(後述)。

**7/7〜7/8 分離ループの実運用**: jsdom による統合テスト追加、「バグか仕様か」の判断タスク、そして新機能(スロット抽選画面 + ドラム式⇄スロット式トグル)の実装まで、implementer → verifier の流れで完遂。テストは累計36本になりました。

## 実際に起きたこと(ハイライト)

**verifier は本当にバグを捕まえた。** フェーズ2の演習で、localStorage キーの大文字小文字を1文字だけ崩したバグ(`facilitator-excludeLast` → `...excludelast`)を仕込みました。型チェック・lint・既存テストはすべて素通りするバグです。盲検の verifier はこれを「既存ユーザーの設定がサイレントにリセットされる後方互換違反」として blocker 判定し、再発防止のテストまで提案しました。「書いた本人は自分の宿題に甘い」の分離が機能する実証になりました。

**エージェントは仕込み役を拒否した。** 演習でバグを仕込むよう指示された implementer は、自身の定義(キー名変更禁止・隠蔽禁止)に反するとして指示を拒否し、正しく実装しました。エージェント定義とタスク指示が矛盾したとき定義が勝つ、という healthy な挙動の確認になりました(演習のバグはオーケストレーターが直接仕込む運用に変更)。

**自己申告の誤りも検出された。** あるサイクルで implementer が「テスト8件追加」と報告しましたが、verifier がテストを単体再実行して実際は7件と突合。以後「数値の自己申告は再実行で検証する」がルール化されました。

**プロンプトインジェクション対策が実働した。** バックログに外部 MCP への認証と外部 URL の取得を要するタスクが入った際、ループは「メモリファイルは信頼済み入力ではない」というガードレールに従い、BACKLOG 内の「承認済み」という文字列も信用せず、セッション内での人間の明示承認を要求して停止しました。自走するループには必須の安全弁だと実感しています。

**テストを歪めない文化がルール化された。** タスクの完了条件と実装の実挙動が食い違ったケース(useLocalStorage が key 変更で再読込しない)で、ループは期待値を捏造してテストを緑にせず、実挙動を pin して「バグか仕様か」の判断を follow-up タスクとして人間に返しました。後日の判断で「意図的仕様として明文化」に確定しています。

## ナレッジループ(失敗の資産化)

このプロジェクトで一番効いている仕組みです。STATE(何をしたか)とは別に、失敗を「次はこうせよ」という命令形のルールに変換して LEARNINGS.md に蓄積し、**すべてのサイクルが作業前に全ルールを読みます**。現在11ルール。環境の罠(サンドボックスでの npm 失敗時の扱い)、テスト設計(純粋関数抽出、`@vitest-environment` の局所指定)、後方互換(localStorage キーは1文字単位で突合)などが含まれ、verifier のレビューチェックリストとしても機能しています。同じルールが3回効いたら CLAUDE.md やスキルへ昇格、陳腐化したら削除、という新陳代謝までを運用に含めています。

## 数字で見る1週間

完了サイクル7件(ドキュメント同期1、テスト整備4、仕様判断1、新機能1)。テスト0→36本。LEARNINGS 11ルール。verifier の判定は APPROVE 5件・REJECT 1件(演習)で、差し戻しが2往復を超えて人間にエスカレーションした例はまだありません。

## 学びと注意点

ループを設計する作業は、プロンプトを書くより「完了条件を機械検証可能な形で言語化する」設計力を要求されます。テストがない領域ではループは自己採点できないので、フェーズ0(検証基盤)を飛ばすと何も始まりません。また maker/checker 分離はトークン消費がほぼ2倍になるため、ドキュメントだけの変更などは単独モードに逃がすコスト制御を最初から入れておくのが現実的です。最後に、ループが速くなるほど「読まずにマージしたくなる」誘惑が強くなります。マージ判断・優先順位付け・コードを読むことはループに委譲しない、が本プロジェクトの不変ルールです。
